# Incident Postmortem — 2026-08-11 — v6.638/v6.640 Dashboard Regressions

## Scope
This postmortem covers the v6.638 and v6.640 Remake Factor dashboard regressions, the failed first v6.641 local recovery procedure, and the client-side root-attribution activation failure discovered during QA.

## Executive summary
The server-side Remake cache and root-attribution backfill remained healthy. Production was unchanged. The regressions were introduced in the browser/UI layer while attempting to improve saved-layout behavior and root-attribution activation.

The primary engineering mistake was treating synthetic source/unit checks as equivalent to real persisted-browser-state QA. The v6.638 and v6.640 releases both modified the shared layout engine to solve localized symptoms. They passed source-level checks but failed real `/dev` QA.

## What failed
### v6.638
A first-paint retry system added several startup and hydration entry points. That violated the single-owner layout lifecycle and produced tiny/scattered cards over an oversized canvas.

### v6.639 recovery
The shared layout editor was restored byte-for-byte to the known-good v6.637 implementation while keeping the larger footer. Real `/dev` visuals substantially recovered. This became the known-good UI baseline for the next recovery.

### v6.640
Two changes were bundled:
1. Root-attribution integration include order was moved.
2. The shared saved-layout migration was changed to place missing cards from live runtime geometry and collision search.

Both intended fixes failed real `/dev` QA. The layout regressed again and root attribution remained inactive.

Read-only layout diagnostics showed the new Attribution Audit was absent from saved layout state and was assigned a runtime top near 2503 px while the surrounding grid shells remained near the top of the page. Existing saved card widths were still reproduced correctly. The giant gap was therefore introduced by the new-card runtime migration path, not by corruption of the user's saved layout.

## Root attribution diagnosis
The raw browser-ready gzip was read directly without rebuilding anything and proved healthy:
- `RemakeFactorBrowserReady v1.35.1`
- 119,589 rows
- `rootProductAttributionEnabled: true`
- root-attribution browser metadata present
- 6,073 root-attribution dictionary entries
- 6,521 rows with attribution index
- 4,215 `ATTRIBUTED_EXACT_ROOT`
- 280 `REVIEW_NON_EXACT_SINGLE_ROOT`
- 1,987 `REVIEW_AMBIGUOUS_ROOT_PRODUCT`
- 39 `UNRESOLVED_UNCONFIRMED_ROOT`
- zero unsafe fallback rows

Known QA case 375669 was present with root case 361499 and `REVIEW_AMBIGUOUS_ROOT_PRODUCT`.

The final dashboard browser state simultaneously reported:
- bridge `v6.637`
- integration `remake-root-attribution-browser-v1.35.2`
- integration active `false`
- state enabled `false`
- state metadata `null`
- zero expanded dashboard rows carrying root-attribution fields

Therefore the remaining attribution defect is client-side after the healthy browser-ready payload is produced. Cache rebuild/backfill is not the fix target.

## Recovery-procedure failure
The first v6.641 local recovery script stopped before modifying files. It failed because:
1. its preflight incorrectly required the entire working tree to be clean even though unrelated untracked files did not conflict with the recovery targets;
2. it was delivered as a large interactive `try/catch/finally` PowerShell paste, which is unsafe for this type of recovery procedure.

No dashboard files were changed by that failed attempt.

## Permanent guardrails
1. Do not modify `SharedDashboardLayoutEditorV6593.html` to solve a localized component-placement defect without separate architecture-level justification and explicit real-browser regression coverage.
2. Synthetic geometry/unit tests are not browser QA and must never be reported as proof that persisted dashboard geometry is safe.
3. Real `/dev` behavior with existing persisted browser layout is the final acceptance authority for layout/platform changes.
4. A disagreement between handoff/server state and runtime state is an immediate stop condition. Diagnose read-only before changing code.
5. After a visual regression, restore the last known-good baseline before continuing feature work.
6. Do not bundle attribution/data-path changes with shared layout-engine changes.
7. Never reset or clear the user's saved layout during routine diagnosis unless separately authorized.
8. Recovery procedures validate only the files they intend to change. Unrelated untracked files are preserved unless they directly conflict with a recovery target.
9. Do not deliver large recovery programs as interactive PowerShell paste. Use a saved `.ps1` or a small sequence of individually inspectable commands.
10. Do not rerun the historical root-attribution backfill or rebuild the browser-ready cache unless separately required and authorized.
11. Do not infer success from source checks when real `/dev` behavior fails.
12. Treat production, GitHub, Apps Script head, browser cache, and persisted browser layout as separate states.

## v6.641 recovery
The approved forward recovery restores:
- `Index.html` exactly to the v6.639 baseline;
- `SharedDashboardLayoutEditorV6593.html` exactly to the v6.637/v6.639 known-good blob;
- `SharedFooter.html` with only the visible release identity changed from v6.640 to v6.641 while retaining the 10.5 px footer styling;
- this postmortem in Git.

The recovery intentionally does not modify root-attribution source, rebuild caches, rerun backfill, change Script Properties or triggers, merge to `main`, or deploy production.

## Remaining work after recovery
1. Deploy v6.641 to Apps Script `/dev` and verify the footer first.
2. Confirm the visual layout matches the known-good v6.639 baseline with the existing persisted browser layout.
3. Keep the shared layout editor frozen while tracing only the client data path that converts the healthy v1.35.1 browser-ready payload into final dashboard state where root-attribution metadata becomes false/null.
4. After the client path is corrected, QA Attribution Audit and Review/Unresolved buckets with real cases.
5. Continue KPI/filter QA independently from layout recovery.
